# Applying DEFRA Copilot Agents to the Packing List Parser Service

---

## Introduction

The **trade-exports-packinglistparser (PLP)** service is a mature Node.js backend built on the DEFRA Core Delivery Platform (CDP). It accepts packing list documents (CSV, Excel, and PDF), discovers the correct parser model, validates business rules, and returns processing outcomes for downstream trade-export systems.

DEFRA has published a curated set of Copilot agents and coding instruction files to GitHub, designed to help development teams align with DEFRA standards, surface inconsistencies, and improve code quality through AI-assisted review.

This exercise imported those agents and instruction files directly into the PLP repository and ran a series of iterative review cycles to answer two questions:

> **How closely does the PLP service already align with DEFRA coding standards?** > **What code-level suggestions would the agents make for existing, production-quality code?**

The service is considered mature and has an established defect history, so a significant reduction in defects was not expected. The primary interest was in **standards alignment visibility** and **code improvement opportunity discovery**.

---

## How to Measure Success

| Metric                                             | Target                                                                                                | Notes                                                                            |
| -------------------------------------------------- | ----------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| Standards gaps identified                          | Named findings against specific DEFRA standard areas                                                  | Did the agents surface concrete, labelled gaps rather than generic observations? |
| Findings actionable and specific                   | Each finding includes a file reference and a suggested fix                                            | Were suggestions precise enough to act on without further investigation?         |
| Platform conflicts distinguished from genuine gaps | CDP-mandated deviations captured in overrides, not raised as actionable findings                      | Were behaviours correct for the CDP platform excluded from the actionable list?  |
| Findings prioritised by severity                   | Blocking > Recommended > Nit ordering applied                                                         | Did the severity labels enable a clear, agreed remediation order?                |
| Token consumption                                  | Full-repository sweeps limited to the initial baseline; subsequent cycles scoped by directory or file | Was the cost of running review cycles sustainable for the team?                  |

Success was defined as gaining **clear, prioritised insight into standards gaps** — not necessarily implementing every finding.

## Approach

### 1. What Was Imported and What Was Generated

The exercise involved a combination of importing assets from the DEFRA GitHub organisation and generating service-specific context files using Copilot itself.

**Imported from DEFRA GitHub:**

- `node-backend.instructions.md` — the baseline instruction file covering language rules, the Hapi framework, security, logging, testing, and environment configuration, applied automatically to all `.js` and `.mjs` files
- `code-reviewer.agent.md` — an agent that performs systematic code review against DEFRA quality criteria, working through categories including correctness, test coverage, security, maintainability, and architecture
- `defra-app-developer.agent.md` — an agent that builds DEFRA-compliant applications following all software development standards, with a pre-commit checklist and explicit guidance on what not to do

**Generated using Copilot (service-specific):**

- `copilot-instructions.md` — the top-level repository instructions file, generated by prompting Copilot with documentation specific to the PLP service (processing flow, integrations, naming conventions, and repository shape). Rather than a single monolithic file, the parser, matcher, and model-headers conventions were deliberately extracted into a separate focused file to keep the main instructions lean and within a manageable size for context processing.
- `parsers-matchers-model-headers.instructions.md` — the extracted, focused instruction file for parser/matcher/model-header conventions, scoped via `applyTo` to only the relevant source directories so it is not loaded unnecessarily for unrelated files

**Introduced during iteration:**

- `local-standards-overrides.instructions.md` — added at a later point in the process, once it became clear that several agent findings conflicted with CDP platform mandates. This file documents each area where the service intentionally deviates from the baseline, the override applied, and the reason it is permitted. Establishing this file gave the agents the context they needed to stop raising those conflicts as actionable findings.

### 2. Iterative Review Cycles

With the agents and instructions in place, a structured two-agent review loop was run repeatedly against the `src/` folder.

**Each cycle followed this sequence:**

1. **Review** — The `code-reviewer` agent was invoked against the `src/` folder. It worked through its nine review categories (PR hygiene, correctness, tests, security, performance, maintainability, architecture, documentation, and accessibility) and produced a list of findings, each labelled as **Blocking**, **Recommended**, or **Nit**, with a file reference, category, and suggested fix.

2. **Triage** — The finding counts by severity were recorded for that cycle. This gave a measurable baseline to compare against subsequent cycles.

3. **Fix** — The `defra-app-developer` agent was then used to implement fixes. The prioritisation rule was:

   - If any **Blocking** findings existed, fix all blockers first.
   - If no blockers remained, address a selection of **Recommended** findings.
   - **Nit**-level findings were noted but not acted on during the cycle.

4. **Repeat** — Once fixes were applied, the review cycle was run again from step 1 to observe how the finding counts changed.

Recording the counts at each cycle made it possible to track whether the codebase was converging toward the standards baseline or whether fixing one finding was generating new ones — which, as noted in the findings section, did occur. This two-agent pattern — reviewer to identify, developer to remediate — proved to be an effective division of responsibility, mirroring a real pull-request review workflow.

**Cycle results**

| Cycle | Blockers | Recommended | Nits | Action taken               |
| ----- | -------- | ----------- | ---- | -------------------------- |
| 1     | 2        | 5           | 2    | Fixed 2 blockers           |
| 2     | 0        | 4           | 2    | Fixed 2 recommended, 1 nit |
| 3     | 2        | 5           | 2    | —                          |

A notable pattern emerged between cycles 2 and 3: despite no blockers remaining after cycle 1 and a net reduction in findings after cycle 2, the third cycle returned 2 new blockers. This illustrates the **compounding recommendations** effect — applying fixes introduced code that the reviewer agent assessed differently in subsequent passes, generating new findings rather than converging toward zero. This was one of the more significant practical observations from the exercise, and reinforced the need to define a stopping threshold rather than targeting a clean review as an end state.

## Findings

### Alignment with DEFRA Standards

Overall, the PLP service demonstrated **strong alignment** with the DEFRA node-backend baseline in its core patterns — ES modules, `async/await`, `@hapi/boom` for error responses, pino-based structured logging, and environment-variable-driven configuration were all already in use.

### Notable Observations

### 1. CDP Platform Constraints Surfaced as Findings

Several findings conflicted directly with CDP platform mandates — the clearest examples being the baseline's recommendation of Jest and Supertest, whereas CDP mandates Vitest and Hapi's `server.inject()` respectively. Beyond those specific conflicts, a broader pattern emerged where behaviours that are deliberately correct for the CDP platform were still flagged. This reflects the agent's default stance: apply the generic DEFRA baseline unless explicitly told otherwise. A well-maintained `local-standards-overrides.instructions.md` is therefore essential before review cycles begin — not an afterthought — to prevent correct platform behaviour from being raised as actionable gaps.

_Success measure: [Platform conflicts distinguished from genuine gaps](#how-to-measure-success)_

### 2. Hapi/Joi Validation and Route Testing Suggestions

The agents consistently suggested adding `joi` schema validation to route payloads at the route level using Hapi's `options.validate.payload` pattern, and flagged route tests that used `.handler` directly rather than `server.inject()`. Both are valid observations against the baseline standard — the validation suggestion in particular was a recurring **Recommended** finding across multiple cycles.

_Success measure: [Standards gaps identified](#how-to-measure-success)_

### 3. Recurring Structural Quality Findings

Test coverage was already significantly higher than the tiered targets the agents enforce before the exercise began, so coverage gaps were not a dominant theme. Where the agents added more value was in consistently identifying recurring structural issues — method and file lengths exceeding recommended thresholds, and repeated constants or magic numbers scattered across the codebase. Importantly, rather than just flagging these as findings, the agents provided concrete approaches for resolving them, such as extracting constants into named modules and breaking oversized functions into focused, single-responsibility helpers.

_Success measure: [Standards gaps identified](#how-to-measure-success)_

### 4. Missing Method Documentation

JSDoc comments on exported functions were flagged repeatedly as **Recommended** findings throughout the cycles. Functions without documented parameters, return types, or descriptions were consistently identified, including in areas of the codebase that had not been recently changed. This category of finding is low-risk and easy to act on incrementally.

_Success measure: [Standards gaps identified](#how-to-measure-success)_

### 5. Token Consumption

Running each full review cycle in a new chat window — as recommended to avoid context drift — meant the agent loaded the full instruction set, all agent files, and the entire `src/` folder content from scratch on every pass. Claude's context window is large, but reviewing a codebase of this size consumed tokens at a rate that becomes significant over many cycles. Targeted, file-scoped or directory-scoped reviews are substantially more token-efficient than full repository sweeps and should be preferred once the initial baseline review has been completed.

## Conclusion

Importing DEFRA Copilot agents into the PLP repository provided **concrete, standards-anchored feedback** on a mature codebase that would otherwise be difficult to obtain without a manual standards audit. The exercise confirmed strong existing alignment in most areas, surfaced a small number of valid and actionable gaps, and highlighted important operational considerations — particularly around platform-specific overrides and token budgeting — that teams should account for before running similar exercises on their own repositories.

The introduction of `local-standards-overrides.instructions.md` was a key lesson: establishing that file up front, before review cycles begin, significantly reduces noise from CDP-mandated deviations and allows the agents to focus on genuinely addressable findings.
